## A. What is this file?

A forward-only PostgreSQL migration for one shared Activity, assignment and completion model.

## B. Why does ARKST need it?

It supports one shared Activity, assignment and completion model. A teacher assigns NPTEL work and assigned students report external completion.

## C. How does it work?

It changes database objects in version order. Identified objects: table: `activity_categories`, `student_scope_memberships`, `activity_capabilities`, `activities` (plus 3 more); function: `active_kind`, `can_manage`, `can_read_activity`, `can_read_assignment` (plus 3 more); policy: `categories_active`, `activities_visible`, `assignments_visible`, `completions_visible` (plus 1 more); index: `student_membership_scope_idx`, `activities_scope_category_idx`, `activities_created_idx`, `activity_assignments_student_idx` (plus 2 more). The SQL is applied or asserted by the local Supabase CLI. Review the exact DDL/RLS/SQL assertions in the original file. This defines categories, student memberships, capability grants, Activities, unique per-student assignments, completion state and actor history. `submit_activity` and `verify_activity` lock and validate transitions. Required verification leaves a student report in `reported` until a different authorized reviewer verifies it.

## E. What happens if I modify this file?

Changing it after application would make database history disagree with Git. Use a new migration and rerun RLS/integration checks.

## F. How do I verify a safe change?

In the isolated local stack, confirm migration history, then run `npm run test:rls` and `npm run test:local`. Never reset a populated database just to test a migration.

## G. Important cautions

Already-applied migrations are historical records: add a new forward migration. Check RLS, grants, `SECURITY DEFINER` search paths and rollback behavior in a disposable environment.
