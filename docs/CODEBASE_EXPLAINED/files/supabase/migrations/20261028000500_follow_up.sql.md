## A. What is this file?

A forward-only PostgreSQL migration for pending-student follow-ups and their history.

## B. Why does ARKST need it?

It supports pending-student follow-ups and their history. A counselor contacts a pending student and later sees that follow-up resolve when the student reports completion.

## C. How does it work?

It changes database objects in version order. Identified objects: table: `activity_follow_ups`, `activity_follow_up_history`; function: `can_follow_up_assignment`, `can_view_follow_up`, `send_activity_follow_ups`, `resolve_activity_follow_up` (plus 1 more); policy: `follow_up_scoped_read`, `follow_up_history_scoped_read`; trigger: `activity_completion_resolve_follow_up`; index: `one_open_follow_up_per_assignment`, `activity_follow_ups_assignment_time`, `follow_up_history_case_idx`. The SQL is applied or asserted by the local Supabase CLI. Review the exact DDL/RLS/SQL assertions in the original file. Follow-ups attach to real Activity assignments, retain history and notify exact recipients. Student completion resolves an open follow-up without erasing the contact record.

## E. What happens if I modify this file?

Changing it after application would make database history disagree with Git. Use a new migration and rerun RLS/integration checks.

## F. How do I verify a safe change?

In the isolated local stack, confirm migration history, then run `npm run test:rls` and `npm run test:local`. Never reset a populated database just to test a migration.

## G. Important cautions

Already-applied migrations are historical records: add a new forward migration. Check RLS, grants, `SECURITY DEFINER` search paths and rollback behavior in a disposable environment.
